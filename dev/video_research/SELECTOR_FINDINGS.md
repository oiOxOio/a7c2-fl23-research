# A7C II 2.01：模式请求追踪与原始指令隔离验证

日期：2026-11-02。已验证的代码提交：`91f4e58bd692b37487101a24fa30ed4498c27466`。

目标是研究 XAVC S 4K、60000/1001 fps、200 Mbps、4:2:2 10bit 的全画幅视角模式；**本轮没有实现该录像目标，没有视频安装入口或可刷入补丁**。所有下文地址均为 CP 虚拟地址，文件偏移为地址减 `0x108000`，不是传感器物理寄存器。

## 1. 证据与执行边界

[官网参考静态分析及隔离仿真 run 41369535775](https://github.com/oiOxOio/a7c2-fl23-research/actions/runs/41369535775) 已完成且成功。[四组离线 CI run 41369542598](https://github.com/oiOxOio/a7c2-fl23-research/actions/runs/41369542598) 也全部成功。两项任务都针对上面的代码提交。

## 2. 找到请求生成到提交的静态连接

原始指令在 `0x48FFC8..0x48FFEE` 连续区域呈现以下关系：

```text
以局部缓冲区 sp+8 为上下文/请求存储
    -> 0xB2D040
    -> 0xB2A93A（调用点 0x48FFD0，r1 为该缓冲区）
    -> 复制生成结果的部分字段
    -> 0x4A8F0C（调用点 0x48FFEE，r0 仍为同一缓冲区）
    -> 0x989D4A(0) 取得实例
    -> SetModeAsync@0x989FDA
```

请求生成附近的 `0xB2AA54` 还直接调用 `0x4C0328`，传入上下文和输出指针。`0x4C03xx..0x4C0Bxx` 的配置选择区域有多个模式家族及条件分支。上述是静态调用点及同一缓冲区的数据流对应，不是已证明用户的特定录像设置实际走过这条路径。

这一步把此前分散的“配置选择”和“请求提交”调查点联系起来，但 AP 菜单设置到这些上下文字段的映射、生命周期状态、实际运行时接收对象仍待确认。

## 3. 不能把条件配对函数当成通用裁切开关

`0xB2A04C..0xB2A17C` 仅在首参数**恰好等于 1**时进行 18 组模式配对；0、2、0xFFFFFFFF 不进行配对。例子包括 `0x5002 -> 0x5004`、`0x5020 -> 0x5021`。该函数不会完成 `0x0B20 -> 0x0B21` 这类视频家族转换。

在更上游 `0x4C071A..0x4C0760`，已有一条条件路径在 `0x0B20/0x0BC0` 和 `0x0B21/0x0BC1` 家族之间直接选择，然后才调用上述配对函数。`0x4BFF90` 附近还有按输入参数选择 `0x0B20/0x0B21` 的路径。

因此，仅使 `0xB2A04C` 不再配对，也不会自动改变上游已经选好的模式。这里仍未把输入标志命名为 APS-C 开关，也没有把上下文中的枚举值擅自解释成 30p/60p。

`0xB2A87C` 的候选选择还依赖 `0xB2A8CC` 的两层查询：首先要求 `0x989E8A(instance, mode)` 返回 1；其策略参数为 1 时，还要求 `0xB0B196(mode)` 返回 1。前者经虚函数槽 +0x10 分派，实际对象身份未闭合。后者使用 `0x121A098` 处的对象指针调用 `0xB0B074`，再判断返回字节是否为 0xFF。其表内容和业务含义还需要追踪，不能直接称为帧率许可证或破解门控。

## 4. 原始叶函数的 248 组隔离执行已通过

这些测试执行的是官网下载 CP 中的原始机器指令，不是把 Python 模型当成固件执行结果。输入对象的状态明确为人工构造，原始模式表及参数表来自固定 CP。

| 原始范围（末地址不含） | 已通过输入案例 | 结论范围 |
| --- | ---: | --- |
| `0x98DF72..0x98DF94` | 34 | 30 个原始 ID、3 个未命中 ID、空列表；编号查找返回索引或 0xFF |
| `0xB2A04C..0xB2A17C` | 184 | 46 个模式值乘 4 个标志值；配对行为与审阅模型一致 |
| `0x98C806..0x98C836` | 30 | 全部 30 个原始模式的整列 staged 参数更新 |

查询函数从接收对象 +4 读取数量、+8 读取 ID 表指针。`0x5002` 查得索引 5，`0x5004` 查得索引 19；未命中及空表返回 0xFF。

参数更新函数输入是**索引**而不是模式 ID，先读取 `0x10FE8E0[index]` 的参数列号，再遍历 `0x10FDCB0` 的 24 字节记录。每个模式执行 129 次一字节写入，测试逐项核对地址、值、顺序及最终读回；每个案例实际执行 784 条指令。目标模式 `0x5002` 对应索引 5、列 2。所有写入仅发生在模拟器 RAM 中，不是传感器总线写入，也没有证明 59.94 Hz 读出。

执行边界：固定 CP 大小和 SHA-256 在导入模拟器前校验；只允许选定的叶函数范围执行；原始代码页不可写；参考表只读；只允许声明的描述符目标字节写入；不允许可写且可执行的原始页面；每次调用有指令数和时间上限。没有把不明辅助函数 stub 成成功。越界、异常控制流、未在限额内返回或非预期写入都会失败。

## 5. 工程验证与复现

本轮新增的 20 项标准库测试在本地普通和 -O 模式均通过。完整离线套件在 CI 共 95 项：94 通过、1 项 `test_exact_original_cp` 因未提供私有原始 CP 环境变量按设计跳过。四组 Windows/Ubuntu、Python 3.11/3.13 均完成普通/-O 测试、CLI smoke 和发布内容检查。

独立官网任务也是先执行这套离线测试，再下载并验证原始 AP/CP，随后进行真实原始指令的 248 组隔离执行。不能把前置跳过项说成已运行，也不能把 248 组执行说成 248 个录像或整机测试。

[selector_trace.py](selector_trace.py) 的 BL/无条件 B.W 扫描使用独立 LLVM 汇编向量交叉检查，保留候选总数和截断信息。半字对齐扫描不保证指令边界或运行可达性；有界反汇编不是完整控制流图。

```bash
# 完全离线：标准库边界/模型回归
python -B -m unittest discover -s dev/video_research -v
python -O -B -m unittest discover -s dev/video_research -v

# 阅读 Sony 条款后，显式下载与隔离执行
python -m pip install pycryptodomex==3.24.1 capstone==5.0.6 unicorn==2.1.4
python -B dev/video_research/selector_trace.py --accept-sony-download-terms --emulate-selectors
```

去掉 `--emulate-selectors` 只做静态分析。生产 `video_research.py` 仍只依赖标准库、离线，不增加 USB 或安装入口。

## 6. 兼容性与下一处研究边界

用户报告的兼容目标为工具 3.0.3 的六款外观、FL2/FL3、原生电子快门声、竖屏拍摄信息。没有读取该机身的实际程序字节或安装事务记录；现有功能安装器未被改写。未来视频补丁与这些功能的字节冲突和行为兼容性尚未完成验证。

下一步要把 AP 的 XAVC S、60000/1001、200 Mbps、4:2:2 10bit 设置映射到请求生成上下文，并确认 `0xB0B074` 查询表和实际运行时对象。随后才是 RAW 有效区域、ISP、行跨度、帧缓冲、硬件编码器和 MP4 时间戳的联动。

仍保持 `movie_path_verified=false`、`recording_verified=false`、`installable=false`。没有生成持久化机身补丁，没有实机开机/摄录/温度/稳定性验收，也没有建立 4K120 或 AF/AE 120 Hz 的实现证据。

初始模式表依据 [chocotan/a7c2-re 固定提交 d79257c](https://github.com/chocotan/a7c2-re/blob/d79257cf6815642b9794fa5b590c9626bfbc2c67/report/2026-10-19-cmos-input-path/tools/verify_opengate_6k.py)。既有 MIT 署名、项目及第三方许可证保持不变。本报告仅记录地址、接口观察和验证结果，不分发 Sony 固件。
